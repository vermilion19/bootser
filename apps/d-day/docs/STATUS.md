# d-day-service — 어디까지 왔나

> 2026-09-15 기준. 착수 순서는 `ARCHITECTURE.md` §9 를 따른다.
> 이 문서는 **목록만** 둔다. 왜 그렇게 정했는지는 각 문서에 있다.

## 한 줄

**주소가 열일곱 개다.** 하늘 일곱 · 축 넷 · 공휴일 조회 넷 · 국가 둘.
전부 실제로 뜬 서버에서 답한다.

**다만 공휴일이 걸린 것들은 아직 빈 답을 준다** — 동기화를 한 번도 안 돌렸다.
읽는 길은 다 섰고 자료만 없다. 하늘과 국가는 자료가 있어서 제대로 답한다.

- 자바 파일 152개 · 테스트 456개 (astro-core 44 · d-day-service 402 · gateway 10)

## 찾은 것 — 짐작과 달랐던 자리

**전부 「그럴듯하게 틀리는」 종류라 적어 둔다.**

### `StructuredTaskScope` 는 JDK 25 에서 아직 프리뷰다

ARCHITECTURE §5.4 가 그것으로 국가별 작업을 묶으라고 적었는데, 재 보니
`jdk-25.0.4` 에서 **프리뷰**다 (JEP 505). 쓰려면 컴파일과 런타임 양쪽에
`--enable-preview` 가 필요하고 **프리뷰로 컴파일한 클래스는 다른 JDK 마이너에서
아예 안 뜬다.** 그런데 그것이 주는 이득(부분 실패 다루기)은 §5.2 가 이미
「작업이 던지지 않게」 만들어 두어 필요 없었다. `invokeAll` 로 가고, 가상
스레드라는 알맹이는 그대로다.

### `source_count` 와 `stored_count` 의 차이는 문서가 말한 것이 아니다

SCHEMA §8.4 는 그 차이를 "A-10 이 거른 비-`Public` 건수" 라고 적었다. 그런데
**A-10 은 비-`Public` 을 거르지 않는다** — 저장하고 노출만 막는다 (§9.3).
그러므로 그 차이는 설계상 0 이다. 두 칼럼은 그대로 두되 무엇을 잡는지를
고쳐 적었다 — **원천이 같은 자연키를 두 번 준 경우**와 **행을 못 만든 경우**다.

### 던진 쪽이 적은 에러 메시지가 응답에서 버려지고 있었다

`CoreException(errorCode, message)` 의 두 번째 인자를 `GlobalExceptionHandler` 가
안 쓴다 — 열거형에 박아 둔 일반론만 나가고 «무엇이 왜 틀렸는지» 가 사라진다.

**범위나 목록처럼 설정에 따라 달라지는 값은 열거형에 못 적는다.** "지금 담은 해:
2025~2028" 같은 것이 그렇다. 그러면 <b>서버가 범위를 정해 놓고 안 알리는 셈</b>이고,
그것은 SPEC §9.9(4) 가 금지한 고장이다.

`ApiResponse.error(errorCode, message)` 를 열고 처리기가 그것을 쓰게 했다. 인자
하나짜리 생성자를 쓴 경우에는 `getMessage()` 가 곧 열거형의 메시지라 달라지는 것이 없다.

### 공유 라이브러리가 날짜 응답을 500 으로 만들고 있었다

첫 HTTP 표면을 세우자마자 드러났다. `libs/storage-redis` 에
`jackson-datatype-jsr310:3.0.0-rc1` 이 못 박혀 있는데, 그것이 ServiceLoader 로
자동 등록되고 그 안의 `JavaTimeModule` 이 rc1 시절의
`SerializationFeature.WRITE_DATES_AS_TIMESTAMPS` 를 참조한다. 3.0.3 에서 그 필드는
`DateTimeFeature` 로 옮겨졌다.

```
NoSuchFieldError: Class tools.jackson.databind.SerializationFeature
                  does not have member field ... WRITE_DATES_AS_TIMESTAMPS
```

**날짜가 든 응답이 전부 500 이 된다.** Jackson 3 에서 JavaTime 지원이 databind 안으로
들어왔으므로 이 모듈은 필요 없다 — 지웠다. `storage-redis` 를 쓰는 다른 서비스도
같은 고장을 안고 있었다.

### 음력 변환이 절기의 12배였다 — 재라고 한 적 없는 값인데 같이 쟀다

설계가 «절기 한 해의 p99 가 20ms 이하면 콜드를 캐시하지 않는다» 로 캐시 정책을
수에 걸어 두었다. **재 보니 2.07ms** — 게이트의 10분의 1이라 그대로 확정했다.

그런데 같이 잰 음력이 **25~32ms** 다. 한 해의 달 구조를 세우려면 삭과 중기를 다
풀어야 해서 절기 한 해보다 무겁다.

캐시 정책은 안 바뀐다(음력도 같은 핫 윈도우에 든다). 바뀌는 것은 **C-7 기념일
등록**이다 — 향후 3년치를 전개하므로 등록 한 번이 75ms+ 이고, 쓰기 경로라 캐시가
안 받아 준다. 착수 8 전에 정한다 (§10-14 로 새로 열었다).

**재라고 한 것만 쟀으면 착수 8 에서 만났을 것이다.**

### 1층 검산점이 「공짜」가 아니었다 — 한국 쪽만

SPEC §B 는 *"코퍼스가 생기면 공짜로 따라오는 검산점"* 이라고 적었다. 일본은 맞다.
**한국은 원천이 일요일에 걸린 공휴일을 빼고 준다** — 설날이 일요일이면 그 날이
목록에 없고 대체공휴일이 뒤에 붙는다. 11해 중 7해가 그랬다.

그래서 「가운데가 음력 1/1」도 「첫날 다음」도 안 된다. 위치로는 못 집는다.
대신 **세 날의 모양**으로 문다 — *(1) `D-1·D·D+1` 중 일요일이 아닌 날은 전부
목록에 있고 (2) 첫날은 `D-1` 또는 `D` 다.* 둘이 함께여야 하루 밀린 것을 잡는다.

**값은 그대로다.** 11해 × 넷이 전부 맞았다.

### AOP 자기호출을 한 번 만들었다가 고쳤다

`SyncOrchestrator` 안에 `@Transactional` 메서드를 두고 같은 클래스에서 불렀다.
2세대 Outbox 가 깨져 있던 바로 그 모양이고 `.claude/rules/behavior.md` 가 경고하는
것도 그것이다. `SyncRunRecorder` 로 갈라서, **오케스트레이터에는
`@Transactional` 이 한 글자도 없게** 했다.

### 캐시 뿌리에 레코드를 놓으면 **읽을 때 터진다**

값 직렬화기의 기본 타이핑이 `NON_FINAL` 이고 레코드는 언제나 final 이다. 처음엔
*"타입 정보가 없어 맵으로 풀리고, 미스로 처리돼 캐시가 조용히 안 듣겠다"* 고 짐작했는데,
재 보니 그보다 나빴다 — `SerializationException` 이 난다.

그리고 `country:all` 은 **TTL 이 없다.** 그런 값이 한 번 들어가면 만료로 풀려날 길이 없어
그 키를 읽는 조회가 영영 터진다. 그래서 둘을 했다.

- `CountryCatalog` 을 레코드가 아니라 클래스로 둔다 (`CountryCatalogSerializationTest`)
- `RedisVersionedCache` 가 **읽다 터지면 미스로 친다** — Redis 가 없을 때도 같다.
  캐시의 사정이 응답을 막아서는 안 된다

### SPEC §5 의 「일요일만 쉬는 1개국」은 인도가 아니라 **우간다**다

수치 셋(195 · 8 · 1)은 착수 3 의 시드가 그대로 재현했다. 그런데 **인도는 Nager 의
204개국에 없다** — CLDR 에서 일요일만 쉬는 대표적인 나라라 괄호에 적혔던 것으로 보인다.
A-7 이 544 를 못 맞혔을 때 "인도가 왜 없지" 로 헤매지 않도록 `CountrySeedFileTest` 가
이 사실을 들고 있다.

## 용어 풀이

이 프로젝트에서 만들어 쓰는 말들. **문서에 자주 나오는데 설명 없이는 알 수 없는 것만** 적는다.

### 검산점

> **남이 공표한 정답지.** 우리가 계산한 값을 거기에 대 본다.

춘분이 몇 시 몇 분인지를 계산해 놓고 **맞는지 알 방법이 없어서** 들였다. 급수 1,161항을 더해
나온 숫자라 눈으로도 손으로도 검산이 안 되고, 버그가 있어도 그럴듯한 숫자가 나온다.

```
우리 계산   2026-03-20 14:46 UTC
NAOJ 공표   2026-03-20 14:46 UTC      ← 이 대조표가 검산점이다
```

**값을 손으로 옮겨 적지 않는다.** 옮기다 틀린 것과 계산이 틀린 것을 구별할 수 없게 되므로,
`tools/fetch-astro-checkpoints.mjs` 가 원천에서 받아 적는다. 같은 규칙이 VSOP87 계수와
ELP2000 계수에도 적용된다 (`tools/gen-vsop87.mjs` · `gen-elp2000.mjs`).

### 1층 검산점 · 2층 검산점

| | 무엇으로 검산하나 | 잡을 수 있는 것 |
| --- | --- | --- |
| **1층** | 한국 설날 · 추석 **날짜** | 날짜가 틀린 것 |
| **2층** | NAOJ 가 공표한 **시각** (분 단위) | 시각이 틀린 것 |

**왜 나눴나 — 1층만으로는 못 잡는 고장이 있다.** ΔT(지구 자전 보정, 2026년에 약 75초)를
통째로 빼고 계산해 보았다.

```
ΔT 를 빼면 — 허용오차(1분)를 넘는 것 45/72 · 날짜가 바뀌는 것 0/72
```

**75초가 틀렸는데 날짜는 72건 전부 그대로다.** 1층만 있었으면 "설날도 추석도 맞으니 됐다" 하고
넘어갔을 것이고, 실제로는 모든 시각이 75초씩 틀린 채였을 것이다.

그래서 **「2층을 먼저 확보하고 착수한다」**가 규칙이 됐다. 만들고 나서 검산점을 찾으면
이미 틀린 것을 정답으로 굳혀 놓고 거기에 맞추게 된다.

**실제로 두 번 건졌다.** 유성우의 기준계 함정(모든 극대가 9시간 이른데 날짜는 그대로) ·
음력 검산점의 유도 오류(20건 맞고 2건 틀렸는데, 틀린 쪽이 우리 계산이 아니라 검산점이었다).

### 축

> **같은 자료를 어느 방향으로 잘라 보느냐.**

공휴일 자료는 하나다. 그것을 무엇으로 묶느냐가 축이고, 정적 사이트의 상단 탭이 그대로 축이다.

| 축 | 묶는 기준 | 답하는 물음 | 검산점 |
| --- | --- | --- | --- |
| 국가 | 나라별 | 한국의 2026년 공휴일은 | — |
| **이름** (A-5) | 이름별 | 크리스마스에 쉬는 나라는 | **178개국** |
| **순위** (A-6) | 나라끼리 견줘 | 공휴일이 제일 많은 나라는 | — |
| **분포** (A-7) | 요일별 | 주말에 겹쳐 날아간 공휴일은 | **544** |
| 하늘 (B) | 천문 | 다음 절기는 | 2층 146건 |

**축은 자료를 하나도 더 만들지 않는다** (SPEC §9.4). `holiday` 표 하나를 다르게 집계할 뿐이고,
그래서 `scripts/schema.sql` 에 `axis` 로 시작하는 표가 한 줄도 없다 — `SchemaIndexTest` 가
그 사실을 문다. 대신 집계가 무거워지고, 그 무게를 캐시가 받는다.

**요일 축의 544 가 특히 중요하다.** 토·일 고정으로 세면 540 이 나온다. 그 네 건의 차이는
금·토가 주말인 8개국과 일요일만 쉬는 1개국(인도) 때문이고, **나라별 주말을 제대로 안 보면
540 이 나온다.** 그래서 `country.weekend_mask` 가 스키마에 있다.

### 게이트웨이 경로 전환

게이트웨이는 정문이다. 들어온 요청을 어느 서비스로 보낼지 정한다. 지금은 **옛 주소**를 본다.

```yaml
- id: d-day-service-route
  predicates:
    - Path=/api/v1/special-days/**      ← 이것을 /api/v1/dday/** 로 바꾸는 일
```

새 설계는 모든 d-day API 를 `/api/v1/dday/` 아래 세 갈래로 둔다 (SPEC §10.1) —
공개 · `me/`(로그인 필수) · `admin/`(권한).

**순서를 일부러 뒤집었다.** 설계 문서는 1→2→3→4 로 적었는데 **4번을 제일 먼저 했다.**

이 게이트웨이에는 *토큰이 없어도 d-day 요청이면 게스트로 통과시킨다*는 동작이 있다. 공개 조회가
대부분이라 맞는 동작인데, 새 주소를 한 줄로 묶으면 **개인 기념일도 거기 들어간다.**

> **경로가 열리기 전에 막아 두면 구멍이 존재한 적이 없게 된다.** 2번을 먼저 하고 4번을
> 나중에 하면 그 사이가 구멍이고, 그 구멍은 터질 때까지 아무도 모른다 — 막혀야 할 요청이
> 통과해도 응답은 200 이다.

2번(실제 주소 전환)을 착수 10 으로 미룬 것은 **지금 열어도 서비스에 API 가 없어 404 만 나기**
때문이다. 표면이 실제로 생겼을 때 연다.

### 창 누적

무료 API 키가 **다음 경기 1건 · 지난 경기 1건**만 준다 (SPEC §12.2). 시즌 전체를 한 번에
받을 수 없으므로, **10분마다 조금씩 받아 쌓는다.**

따라오는 것이 둘이다. **같은 경기를 하루 144번 다시 본다** — 그래서 안 바뀌었으면 쓰지 않는
장치(`source_hash`)가 필요하다. 그리고 **"사라졌다"를 관측할 수 없다** — 원천이 다음 1건만
주므로, `sport_event` 는 소프트 삭제를 하지 않는다.

### 버전 플립

캐시를 지우는 방법. 개별 키를 찾아 지우는 대신 **버전 번호를 하나 올린다.**

```
ax:rank:2026:v7   ← 옛 키. TTL 로 저절로 사라진다
ax:rank:2026:v8   ← 버전을 올리면 여기를 본다
```

개별 삭제를 안 하는 까닭은 **동기화 한 번이 어느 키를 더럽히는지 계산할 수 없기** 때문이다.
스위스 공휴일 하나가 바뀌면 이름 축 · 순위 축 · 요일 축이 같이 틀려진다.

**그리고 새 버전에 먼저 심고 나서 뒤집는다.** 그냥 올리면 그 순간 전부 캐시 미스라
제일 무거운 질의가 한꺼번에 몰린다.

### 소프트 삭제

지울 때 행을 없애지 않고 `deleted_at` 에 시각만 찍는다. **원천이 되살릴 수 있는 자료에만** 쓴다.

| | `holiday` | `anniversary` |
| --- | --- | --- |
| 삭제의 뜻 | 원천이 이번 주에 안 줬다 | **사람이 지웠다** |
| 되살아날 수 있나 | 있다 | 없다 |
| 그래서 | 소프트 삭제 | **진짜로 지운다** |

### 급감 가드

원천이 **HTTP 200 으로 빈 배열을 주는** 경우가 있다. 그대로 믿으면 그 나라 공휴일이 전멸한다.
조용히. 그래서 **직전 성공 회차 대비 절반 미만이면 반영하지 않는다.**

*에러가 아니라 그럴듯한 데이터라서 위험하다* — 원천이 200 으로 헛소리하는 일이 이 두 API 에서
이미 한 번 관측됐다 (SPEC §12.3).

# d-day-service — 어디까지 왔나

> 2026-09-16 기준. 착수 순서는 `ARCHITECTURE.md` §9 를 따른다.
> 이 문서는 **목록만** 둔다. 왜 그렇게 정했는지는 각 문서에 있다.

## 한 줄

**주소가 서른세 개다.** 하늘 일곱 · 축 넷 · 공휴일 넷 · 국가 둘 · 개인 기념일 넷 ·
경기 다섯 · 관심 셋 · 운영자 셋 · **통합 검색 하나**.

**착수 순서(0~10)가 끝났고, 1차 밖으로 밀어 뒀던 검색(E-2)도 만들었다.**

**자료가 걸린 것들이 아직 빈 답을 준다** — 공휴일 동기화도 경기 동기화도 한 번도 안
돌렸다 (앞은 DB 가 없고 뒤는 API 키가 없다). 하늘 · 국가 · 기념일 · 관심은 제대로
답한다.

- 자바 파일 199개 (테스트 55개 파일) · 테스트 **652개** (d-day-service 586 ·
  astro-core 44 · gateway 15 · notification-service 7) · 건너뜀 4 (Docker 필요)
- 커밋 26개 — **이번 것(검색)은 아직 안 했다**

## 찾은 것 — 짐작과 달랐던 자리

**전부 「그럴듯하게 틀리는」 종류라 적어 둔다.**

### `StructuredTaskScope` 는 JDK 25 에서 아직 프리뷰다

ARCHITECTURE §5.4 가 그것으로 국가별 작업을 묶으라고 적었는데, 재 보니
`jdk-25.0.4` 에서 **프리뷰**다 (JEP 505). 쓰려면 컴파일과 런타임 양쪽에
`--enable-preview` 가 필요하고 **프리뷰로 컴파일한 클래스는 다른 JDK 마이너에서
아예 안 뜬다.** 그런데 그것이 주는 이득(부분 실패 다루기)은 §5.2 가 이미
「작업이 던지지 않게」 만들어 두어 필요 없었다. `invokeAll` 로 가고, 가상
스레드라는 알맹이는 그대로다.

### `source_count` 와 `stored_count` 의 차이는 문서가 말한 것이 아니다

SCHEMA §8.4 는 그 차이를 "A-10 이 거른 비-`Public` 건수" 라고 적었다. 그런데
**A-10 은 비-`Public` 을 거르지 않는다** — 저장하고 노출만 막는다 (§9.3).
그러므로 그 차이는 설계상 0 이다. 두 칼럼은 그대로 두되 무엇을 잡는지를
고쳐 적었다 — **원천이 같은 자연키를 두 번 준 경우**와 **행을 못 만든 경우**다.

### `ON DELETE CASCADE` 가 H2 에는 없다 — 테스트와 운영이 다르게 돌았다

투영을 `@ManyToOne` 으로 매핑하지 않았으므로 H2 `create-drop` 은 FK 도 연쇄도
안 만든다. `scripts/schema.sql` 의 `CASCADE` 는 **PostgreSQL 에만 있다.**

그래서 «부모를 지우면 투영도 지워진다» 가 테스트에서만 거짓이었다 — 운영에서는
맞고 테스트에서는 틀린다. **반대였으면 더 나빴을 것**이다.

앱이 직접 지우게 고쳤다. 두 DB 가 같이 돌고, `CASCADE` 는 다른 경로로 부모가
지워질 때의 안전망으로 남는다. SCHEMA §1.2 가 생성 칼럼을 버린 것과 같은 종류의
함정이다.

### 던진 쪽이 적은 에러 메시지가 응답에서 버려지고 있었다

`CoreException(errorCode, message)` 의 두 번째 인자를 `GlobalExceptionHandler` 가
안 쓴다 — 열거형에 박아 둔 일반론만 나가고 «무엇이 왜 틀렸는지» 가 사라진다.

**범위나 목록처럼 설정에 따라 달라지는 값은 열거형에 못 적는다.** "지금 담은 해:
2025~2028" 같은 것이 그렇다. 그러면 <b>서버가 범위를 정해 놓고 안 알리는 셈</b>이고,
그것은 SPEC §9.9(4) 가 금지한 고장이다.

`ApiResponse.error(errorCode, message)` 를 열고 처리기가 그것을 쓰게 했다. 인자
하나짜리 생성자를 쓴 경우에는 `getMessage()` 가 곧 열거형의 메시지라 달라지는 것이 없다.

### 공유 라이브러리가 날짜 응답을 500 으로 만들고 있었다

첫 HTTP 표면을 세우자마자 드러났다. `libs/storage-redis` 에
`jackson-datatype-jsr310:3.0.0-rc1` 이 못 박혀 있는데, 그것이 ServiceLoader 로
자동 등록되고 그 안의 `JavaTimeModule` 이 rc1 시절의
`SerializationFeature.WRITE_DATES_AS_TIMESTAMPS` 를 참조한다. 3.0.3 에서 그 필드는
`DateTimeFeature` 로 옮겨졌다.

```
NoSuchFieldError: Class tools.jackson.databind.SerializationFeature
                  does not have member field ... WRITE_DATES_AS_TIMESTAMPS
```

**날짜가 든 응답이 전부 500 이 된다.** Jackson 3 에서 JavaTime 지원이 databind 안으로
들어왔으므로 이 모듈은 필요 없다 — 지웠다. `storage-redis` 를 쓰는 다른 서비스도
같은 고장을 안고 있었다.

### 음력 변환이 절기의 12배였다 — 재라고 한 적 없는 값인데 같이 쟀다

설계가 «절기 한 해의 p99 가 20ms 이하면 콜드를 캐시하지 않는다» 로 캐시 정책을
수에 걸어 두었다. **재 보니 2.07ms** — 게이트의 10분의 1이라 그대로 확정했다.

그런데 같이 잰 음력이 **25~32ms** 다. 한 해의 달 구조를 세우려면 삭과 중기를 다
풀어야 해서 절기 한 해보다 무겁다.

캐시 정책은 안 바뀐다(음력도 같은 핫 윈도우에 든다). 바뀌는 것은 **C-7 기념일
등록**이다 — 향후 3년치를 전개하므로 등록 한 번이 75ms+ 이고, 쓰기 경로라 캐시가
안 받아 준다. 착수 8 전에 정한다 (§10-14 로 새로 열었다).

**재라고 한 것만 쟀으면 착수 8 에서 만났을 것이다.**

### 1층 검산점이 「공짜」가 아니었다 — 한국 쪽만

SPEC §B 는 *"코퍼스가 생기면 공짜로 따라오는 검산점"* 이라고 적었다. 일본은 맞다.
**한국은 원천이 일요일에 걸린 공휴일을 빼고 준다** — 설날이 일요일이면 그 날이
목록에 없고 대체공휴일이 뒤에 붙는다. 11해 중 7해가 그랬다.

그래서 「가운데가 음력 1/1」도 「첫날 다음」도 안 된다. 위치로는 못 집는다.
대신 **세 날의 모양**으로 문다 — *(1) `D-1·D·D+1` 중 일요일이 아닌 날은 전부
목록에 있고 (2) 첫날은 `D-1` 또는 `D` 다.* 둘이 함께여야 하루 밀린 것을 잡는다.

**값은 그대로다.** 11해 × 넷이 전부 맞았다.

### 필수 파라미터를 안 보내면 **500 이 나가고 있었다** — 저장소 전체가

검색 주소에 `q` 를 안 보내 보다 드러났다. `@RequestParam` 이 없으면 Spring 이
`MissingServletRequestParameterException` 을 던지는데, `GlobalExceptionHandler` 에
그것을 받는 자리가 없어 **`Exception` 처리기가 500 「서버 내부 오류가 발생했습니다」**
로 냈다.

**부르는 쪽의 실수인데 서버 탓으로 나간다.** 빠뜨린 사람은 자기 요청을 안 보고
우리 로그를 의심한다. 타입이 안 맞는 경우(`?year=올해`)도 같았다.

둘 다 400 으로 바꿨다. **`d-day` 에서 드러났지만 이 저장소의 모든 서비스가 같은
고장을 안고 있었다** — 「던진 쪽이 적은 메시지가 버려지던 것」과 같은 자리에서 나온
같은 종류의 고장이다.

### `@MockitoBean` 으로 둔 인터셉터가 **모든 요청을 끊었다**

검색 컨트롤러 테스트 열둘 중 **열하나가 한 번에 깨졌다.** `AdminOnlyInterceptor` 를
가짜로 뒀는데, Mockito 가 만든 `preHandle` 의 기본 반환이 `false` 라 **요청이
컨트롤러에 닿기 전에 전부 끊겼다.**

인터셉터는 「통과시킬지」를 boolean 으로 답하는 자리라 <b>기본값이 곧 「전부
막는다」</b>다. 가짜를 두는 순간 그 뜻이 뒤집힌다. 진짜를 들여 고쳤다 —
`@AdminOnly` 가 안 붙은 컨트롤러는 어차피 그냥 지나간다.

### 검색이 「한국」을 못 찾는다 — 코드가 아니라 자료다

CLDR 의 한국어 나라 이름은 **「대한민국」**이다. 부분 문자열로 보므로 「대한」은
걸리고 **「한국」은 안 걸린다.**

별칭 표를 두면 풀리지만 그것은 자료를 더하는 일이고, <b>코드가 틀린 것처럼 보이는
자리라 적어 둔다.</b> 「검색이 이상하다」로 코드를 뒤지는 일이 없게.

### 켤 수 없는 것이 **고장으로 적히고 있었다**

착수 9 를 다 만들고 `out` 프로필로 띄워 `POST /admin/sync/sport-event` 를 눌러 봤다.
키가 없으니 「건너뜀」 한 건으로 끝나는 것이 맞는데, **회차가 `FAILED` 로 적혔다.**

`SyncRun.decide` 가 `ok == 0` 이면 실패로 보기 때문이다. 그 규칙은 공휴일을 보고
만든 것이다 — 1,020개가 전부 실패한 회차는 실패다. 그런데 **「할 일이 없었다」도
`ok == 0`** 이다.

그대로 두면 10분마다 「실패」가 쌓이고, **그 표는 못 읽는 표가 된다** — 기능을 끌 수
있게 만든 이유가 통째로 무너진다. 「전부 건너뜀」을 `SUCCEEDED` 로 갈랐다. 왜
건너뛰었는지는 항목 한 건이 문장으로 들고 있다.

```
status   SUCCEEDED     itemTotal 1 · itemOk 0
item     SKIPPED       "dday.sync.sports.api-key 가 없거나 켠 리그가 없다"
```

**`total == 0` 은 여전히 실패다.** 항목이 하나도 안 만들어진 것은 시도조차 안 했다는
뜻이고(공휴일의 «국가 시드가 비어 있다» 가 그 모양), 그것을 성공으로 적으면
**아무 일도 안 하는 동기화가 조용히 성공한다.**

**띄워 보지 않았으면 못 찾았다.** 테스트는 `SyncOutcome` 의 수를 물었고, 그 수에서
상태를 뽑는 규칙이 새 상황을 모른다는 것은 **주소를 눌러 봐야 보였다.**

### `out` 프로필은 「Redis 없이」가 아니었다 — 이 PC 에 Redis 가 떠 있다

위의 수동 트리거가 **돌아간 것 자체가 예상 밖**이었다. `out` 프로필 주석은
「DB 도 Redis 도 없이 띄워 보는 프로필」이라고 적혀 있고, ShedLock 의 락 제공자는
Redis 를 쓴다 — 없으면 락을 잡다 터져야 한다.

6379를 확인해 보니 **떠 있었다.** 그래서 회차가 실제로 Redis 락을 잡고 돌았다.
그 프로필이 끄는 것은 **릴레이 · 시드 · 스케줄**이고 Redis 자체를 안 쓰게 만드는
것이 아니다 — 캐시는 읽다 터지면 미스로 치므로(위 「캐시 뿌리에…」) Redis 가 없어도
응답이 나가지만, **락은 그렇지 않다.**

### 멱등키가 §3.5 의 규칙대로면 **순연이 두 번째부터 조용히 사라진다**

ARCHITECTURE §3.5 는 경기 변경의 멱등키를 `(externalId, fromTs, toTs)` 로 적었다.
그대로 두면 `POSTPONED: no→yes` 가 한 번 적힌 뒤로 **며칠 뒤의 같은 전이가
「이미 보냈다」로 걸러진다.**

우천 순연은 KBO 에서 일상이고 (SPEC §12.1 이 KBO 를 고른 근거가 바로 그것이다)
**순연 → 해제 → 다시 순연은 서로 다른 사실**이다. SCHEMA §6.3 이 `date_change` 에
유일 제약을 일부러 안 걸었는데, **멱등키가 그것을 뒤에서 되돌리고 있었다.**

키에 **탐지한 날(UTC)** 을 더했다. 원래 목적은 그대로다 — 창 누적이 같은 경기를
하루에 여러 번 봐도 **안 바뀐 건은 `source_hash` 에서 이미 걸려** 멱등키까지 오지
않는다. 같은 날 같은 전이가 두 번 오는 것은 우리 쪽 재실행일 때뿐이고 그것은
여전히 걸러진다 (`sameDayRepeatIsFolded` · `repeatedTransitionOnAnotherDaySurvives`).

### 문서가 세 곳에서 근거로 들던 `admin/sync` 주소가 없었다

`SchedulerConfig` · `SyncOrchestrator` · `SyncTarget` 이 모두 「`@SchedulerLock` 을
안 쓰고 락을 오케스트레이터에 둔 까닭은 **수동 트리거가 같은 이름의 락을 잡아야**
하기 때문이다」(§5.6) 를 주석으로 들고 있었다. 그런데 `POST /admin/sync/{target}` 이
**한 줄도 없었다.**

근거가 가리키는 것이 없으면 그 설계가 맞는지 확인할 방법이 없다. 착수 10 에서
같이 세웠다 — `POST` 는 이미 돌고 있으면 **409**(200 이 아니다), `GET .../items` 는
**안 된 항목만** 준다(한 회차가 1,020 항목이라 전부 주면 사람이 못 읽는다).

### 게이트웨이가 d-day 로 보내는 경로가 죽은 주소 하나뿐이었다

라우팅 predicate 가 `/api/v1/special-days/**` 였다. 착수 6~9 가 낸 주소 32개는
**게이트웨이를 통해 닿을 수 없었다** — 서비스를 직접 부를 때만 됐다. 착수 10 이
그것을 옮겼고, 옛 경로가 정말 지워졌는지를 테스트가 문다 (`oldPathIsGone`).

같이 고친 것 하나 — `PATH_SERVICE_MAPPING` 이 `Map.of` 였다. 순서 없는 해시맵을
`entrySet` 으로 순회하므로 **겹치는 패턴을 넣는 순간 어느 것이 먼저 맞을지 JVM 이
정한다.** 「겹치는 것을 넣지 마라」를 주석으로만 지키는 것은 언젠가 깨지므로
순서 있는 목록(`gateway.jwt.path-services`)으로 바꿨다 — **먼저 적은 것이 이긴다**가
규칙이 되고, 그 규칙은 읽는 사람이 확인할 수 있다.

### `@WebMvcTest` 는 `WebMvcConfigurer` 를 알아서 끌어온다

`AdminOnly` 인터셉터를 `WebConfig` 에 등록하자 **다른 컨트롤러 테스트 여섯 개가
401 로 깨졌다.** `@WebMvcTest` 는 컨트롤러만 띄우는 줄 알았는데 `WebMvcConfigurer`
구현은 명시적으로 `@Import` 하지 않아도 포함된다.

깨진 것이 옳다 — 검사가 실제로 걸린다는 뜻이다. 테스트에 헤더를 붙여 고쳤다.
**검사를 끄고 테스트하면 「검사가 켜진 상태에서 이 주소가 도는지」를 묻지 않은
셈**이 되므로, 설정으로 끄는 길(`dday.admin.require-role`)은 띄워 보는 프로필에만 쓴다.

### AOP 자기호출을 한 번 만들었다가 고쳤다

`SyncOrchestrator` 안에 `@Transactional` 메서드를 두고 같은 클래스에서 불렀다.
2세대 Outbox 가 깨져 있던 바로 그 모양이고 `.claude/rules/behavior.md` 가 경고하는
것도 그것이다. `SyncRunRecorder` 로 갈라서, **오케스트레이터에는
`@Transactional` 이 한 글자도 없게** 했다.

### 캐시 뿌리에 레코드를 놓으면 **읽을 때 터진다**

값 직렬화기의 기본 타이핑이 `NON_FINAL` 이고 레코드는 언제나 final 이다. 처음엔
*"타입 정보가 없어 맵으로 풀리고, 미스로 처리돼 캐시가 조용히 안 듣겠다"* 고 짐작했는데,
재 보니 그보다 나빴다 — `SerializationException` 이 난다.

그리고 `country:all` 은 **TTL 이 없다.** 그런 값이 한 번 들어가면 만료로 풀려날 길이 없어
그 키를 읽는 조회가 영영 터진다. 그래서 둘을 했다.

- `CountryCatalog` 을 레코드가 아니라 클래스로 둔다 (`CountryCatalogSerializationTest`)
- `RedisVersionedCache` 가 **읽다 터지면 미스로 친다** — Redis 가 없을 때도 같다.
  캐시의 사정이 응답을 막아서는 안 된다

### SPEC §5 의 「일요일만 쉬는 1개국」은 인도가 아니라 **우간다**다

수치 셋(195 · 8 · 1)은 착수 3 의 시드가 그대로 재현했다. 그런데 **인도는 Nager 의
204개국에 없다** — CLDR 에서 일요일만 쉬는 대표적인 나라라 괄호에 적혔던 것으로 보인다.
A-7 이 544 를 못 맞혔을 때 "인도가 왜 없지" 로 헤매지 않도록 `CountrySeedFileTest` 가
이 사실을 들고 있다.

| 어디 | 몇 개 | 대표적인 것 |

**이번에 닫힌 셋.**

| | 무엇 | 답 |

| §10-2 | `notification-service` 에 d-day 리스너를 넣을 것인가 | **넣었다.** 본문 타입은 `libs/core-web` 에 — 양쪽이 따로 적으면 갈라지는 날 컨슈머가 필드 하나를 조용히 잃는다 |

**검색이 §10-13 을 닫았다** — 색인도 캐시도 **둘 다 「안 한다」**로. 안 하는 쪽을
고른 것이라 나중에 뒤집기 쉽다: `SearchScope` 가 공개와 개인을 이미 갈라 두었고
(캐시), 소스는 포트라 구현만 바꾸면 된다(색인).

**남은 것 중 셋은 「관측 후」다** — 급감 가드 임계치(§10-10) · fan-out 상한(§10-11) ·
이름 문턱(§10-9). 전부 **자료가 차고 사람이 쓴 뒤**에만 정할 수 있다.

**이름 문턱(§10-9)은 검색이 한 번 더 끌어올렸다.** 한국어 라벨이 없는 공휴일 이름은
<b>영어로만 검색된다</b> — 문턱을 어디 두느냐가 이제 「한국어로 찾히는 이름이
몇이냐」이기도 하다.

**§10-3(공개 갈래에서 `requiredService` 검사를 건너뛸 것인가)은 열어 둔다.**
게이트웨이 필터의 인가 모델을 바꾸는 일이라 d-day 의 범위가 아니다 — 지금은
**비로그인은 되는데 로그인하면 403 이 될 수 있는** 자리가 남아 있다 (§7.5).

~~**S-6 이 제일 급하다**~~ — **닫혔다 (2026-09-15, SCHEMA §14).** 착수 3 이 `country` 에
204행을 넣으면 「빈 DB」가 끝나므로 그 앞에서 닫았다.

**이제 급한 것은 `SCHEMA.md` §13.1 의 실측 게이트 5개다.** 전부 **코퍼스가 찬 뒤**에만
잴 수 있고, 그중 4번(자연키 충돌 0)에서 위반이 나오면 **스키마가 틀린 것**이다.
자료가 찬 뒤에 유일 인덱스를 바꾸는 것은 이제 §14 의 변경 스크립트가 되고, 그 첫 변경이
§14.7 의 넷을 데려와야 한다.

**그런데 그것을 잴 수 있는 시점이 코드가 아니라 환경에 걸려 있다.** 공휴일 동기화는
PostgreSQL 이 있어야 하고(지금은 인메모리 H2 만 쓴다), 경기 동기화는 API 키가 있어야
하고, 사슬을 끝까지 밟으려면 Kafka 를 띄워야 한다. **코드로 더 할 수 있는 것은
착수 순서에 남아 있지 않다.**

## 용어 풀이

이 프로젝트에서 만들어 쓰는 말들. **문서에 자주 나오는데 설명 없이는 알 수 없는 것만** 적는다.

### 검산점

> **남이 공표한 정답지.** 우리가 계산한 값을 거기에 대 본다.

춘분이 몇 시 몇 분인지를 계산해 놓고 **맞는지 알 방법이 없어서** 들였다. 급수 1,161항을 더해
나온 숫자라 눈으로도 손으로도 검산이 안 되고, 버그가 있어도 그럴듯한 숫자가 나온다.

```
우리 계산   2026-03-20 14:46 UTC
NAOJ 공표   2026-03-20 14:46 UTC      ← 이 대조표가 검산점이다
```

**값을 손으로 옮겨 적지 않는다.** 옮기다 틀린 것과 계산이 틀린 것을 구별할 수 없게 되므로,
`tools/fetch-astro-checkpoints.mjs` 가 원천에서 받아 적는다. 같은 규칙이 VSOP87 계수와
ELP2000 계수에도 적용된다 (`tools/gen-vsop87.mjs` · `gen-elp2000.mjs`).

### 1층 검산점 · 2층 검산점

| | 무엇으로 검산하나 | 잡을 수 있는 것 |
| --- | --- | --- |
| **1층** | 한국 설날 · 추석 **날짜** | 날짜가 틀린 것 |
| **2층** | NAOJ 가 공표한 **시각** (분 단위) | 시각이 틀린 것 |

**왜 나눴나 — 1층만으로는 못 잡는 고장이 있다.** ΔT(지구 자전 보정, 2026년에 약 75초)를
통째로 빼고 계산해 보았다.

```
ΔT 를 빼면 — 허용오차(1분)를 넘는 것 45/72 · 날짜가 바뀌는 것 0/72
```

**75초가 틀렸는데 날짜는 72건 전부 그대로다.** 1층만 있었으면 "설날도 추석도 맞으니 됐다" 하고
넘어갔을 것이고, 실제로는 모든 시각이 75초씩 틀린 채였을 것이다.

그래서 **「2층을 먼저 확보하고 착수한다」**가 규칙이 됐다. 만들고 나서 검산점을 찾으면
이미 틀린 것을 정답으로 굳혀 놓고 거기에 맞추게 된다.

**실제로 두 번 건졌다.** 유성우의 기준계 함정(모든 극대가 9시간 이른데 날짜는 그대로) ·
음력 검산점의 유도 오류(20건 맞고 2건 틀렸는데, 틀린 쪽이 우리 계산이 아니라 검산점이었다).

### 축

> **같은 자료를 어느 방향으로 잘라 보느냐.**

공휴일 자료는 하나다. 그것을 무엇으로 묶느냐가 축이고, 정적 사이트의 상단 탭이 그대로 축이다.

| 축 | 묶는 기준 | 답하는 물음 | 검산점 |
| --- | --- | --- | --- |
| 국가 | 나라별 | 한국의 2026년 공휴일은 | — |
| **이름** (A-5) | 이름별 | 크리스마스에 쉬는 나라는 | **178개국** |
| **순위** (A-6) | 나라끼리 견줘 | 공휴일이 제일 많은 나라는 | — |
| **분포** (A-7) | 요일별 | 주말에 겹쳐 날아간 공휴일은 | **544** |
| 하늘 (B) | 천문 | 다음 절기는 | 2층 146건 |

**축은 자료를 하나도 더 만들지 않는다** (SPEC §9.4). `holiday` 표 하나를 다르게 집계할 뿐이고,
그래서 `scripts/schema.sql` 에 `axis` 로 시작하는 표가 한 줄도 없다 — `SchemaIndexTest` 가
그 사실을 문다. 대신 집계가 무거워지고, 그 무게를 캐시가 받는다.

**요일 축의 544 가 특히 중요하다.** 토·일 고정으로 세면 540 이 나온다. 그 네 건의 차이는
금·토가 주말인 8개국과 일요일만 쉬는 1개국(인도) 때문이고, **나라별 주말을 제대로 안 보면
540 이 나온다.** 그래서 `country.weekend_mask` 가 스키마에 있다.

### 게이트웨이 경로 전환

게이트웨이는 정문이다. 들어온 요청을 어느 서비스로 보낼지 정한다. **옛 주소를 보고
있었다** — 착수 10 에서 바꿨다.

```yaml
- id: d-day-service-route
  predicates:
-   - Path=/api/v1/special-days/**      ← 죽은 주소였다
+   - Path=/api/v1/dday/**
```

**바꾸기 전까지 착수 6~9 가 낸 주소 32개는 게이트웨이를 통해 닿을 수 없었다.**
서비스를 직접 부를 때만 됐다.

새 설계는 모든 d-day API 를 `/api/v1/dday/` 아래 세 갈래로 둔다 (SPEC §10.1) —
공개 · `me/`(로그인 필수) · `admin/`(권한).

**순서를 일부러 뒤집었다.** 설계 문서는 1→2→3→4 로 적었는데 **4번을 제일 먼저 했다.**

이 게이트웨이에는 *토큰이 없어도 d-day 요청이면 게스트로 통과시킨다*는 동작이 있다. 공개 조회가
대부분이라 맞는 동작인데, 새 주소를 한 줄로 묶으면 **개인 기념일도 거기 들어간다.**

> **경로가 열리기 전에 막아 두면 구멍이 존재한 적이 없게 된다.** 2번을 먼저 하고 4번을
> 나중에 하면 그 사이가 구멍이고, 그 구멍은 터질 때까지 아무도 모른다 — 막혀야 할 요청이
> 통과해도 응답은 200 이다.

2번(실제 주소 전환)을 착수 10 으로 미룬 것은 **먼저 열어도 서비스에 API 가 없어 404 만 나기**
때문이다. 표면이 실제로 생겼을 때 열었다.

**같이 고친 것 하나.** 경로 → 서비스 지도가 `Map.of` 였다. 순서 없는 해시맵을
`entrySet` 으로 순회하므로 **겹치는 패턴을 넣는 순간 어느 것이 먼저 맞을지 JVM 이
정한다.** 「겹치는 것을 넣지 마라」를 주석으로만 지키는 것은 언젠가 깨지므로 순서
있는 목록(`gateway.jwt.path-services`)으로 바꿨다 — **먼저 적은 것이 이긴다**가
규칙이 되고, 그 규칙은 읽는 사람이 확인할 수 있다.

### 창 누적

무료 API 키가 **다음 경기 1건 · 지난 경기 1건**만 준다 (SPEC §12.2). 시즌 전체를 한 번에
받을 수 없으므로, **10분마다 조금씩 받아 쌓는다.**

따라오는 것이 둘이다. **같은 경기를 하루 144번 다시 본다** — 그래서 안 바뀌었으면 쓰지 않는
장치(`source_hash`)가 필요하다. 그리고 **"사라졌다"를 관측할 수 없다** — 원천이 다음 1건만
주므로, `sport_event` 는 소프트 삭제를 하지 않는다.

### 2단 발행

경기 일정이 바뀌면 **두 번 나간다.**

```
1단 · 사실   경기가 연기됐다        → dday.release.changed         수신자가 없다
2단 · 의도   A 씨에게 알려야 한다   → dday.notification.requested  회원마다 한 건
```

**동기화 트랜잭션에서 한 번에 펼치지 않는 까닭**은 관심자 수에 비례해 그 트랜잭션이
길어지기 때문이다 — 인기 팀 하나가 동기화 전체를 붙들고, 재시도 단위도 통째가 된다.

나누면 셋을 얻는다. 동기화가 관심자 수와 **무관**해지고, 펼치기가 Kafka 컨슈머라
**혼자 재시도되고 끝내 실패하면 DLT 로** 가고, 1단에 소비자를 더 붙일 수 있다
(나중의 검색 색인이 그 이벤트를 탄다).

**관심은 경기에도 걸고 팀에도 건다.** 한화 팬은 경기 하나를 고른 적이 없으므로,
1단이 **그 경기에 나온 팀 id 를 같이 싣는다** — 2단이 경기를 다시 조회하면 그
사이에 경기가 지워졌을 때 알림이 통째로 사라진다. 사실은 이미 일어났는데.

### 버전 플립

캐시를 지우는 방법. 개별 키를 찾아 지우는 대신 **버전 번호를 하나 올린다.**

```
ax:rank:2026:v7   ← 옛 키. TTL 로 저절로 사라진다
ax:rank:2026:v8   ← 버전을 올리면 여기를 본다
```

개별 삭제를 안 하는 까닭은 **동기화 한 번이 어느 키를 더럽히는지 계산할 수 없기** 때문이다.
스위스 공휴일 하나가 바뀌면 이름 축 · 순위 축 · 요일 축이 같이 틀려진다.

**그리고 새 버전에 먼저 심고 나서 뒤집는다.** 그냥 올리면 그 순간 전부 캐시 미스라
제일 무거운 질의가 한꺼번에 몰린다.

### 소프트 삭제

지울 때 행을 없애지 않고 `deleted_at` 에 시각만 찍는다. **원천이 되살릴 수 있는 자료에만** 쓴다.

| | `holiday` | `anniversary` |
| --- | --- | --- |
| 삭제의 뜻 | 원천이 이번 주에 안 줬다 | **사람이 지웠다** |
| 되살아날 수 있나 | 있다 | 없다 |
| 그래서 | 소프트 삭제 | **진짜로 지운다** |

### 급감 가드

원천이 **HTTP 200 으로 빈 배열을 주는** 경우가 있다. 그대로 믿으면 그 나라 공휴일이 전멸한다.
조용히. 그래서 **직전 성공 회차 대비 절반 미만이면 반영하지 않는다.**

*에러가 아니라 그럴듯한 데이터라서 위험하다* — 원천이 200 으로 헛소리하는 일이 이 두 API 에서
이미 한 번 관측됐다 (SPEC §12.3).

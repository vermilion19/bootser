## 1. 한 문장

**정적 사이트가 빌드 타임에 굳혀 두던 것을 서버가 다시 소유하고, 그 위에 정적으로는
원리적으로 불가능한 것 — 개인 · 가변 · 실시간 — 을 얹는다.**

내는 것은 **JSON API 뿐이다.** 화면은 나중에 별도 프론트가 맡는다.

## 2. 목적 — 기능을 비계로 쓴다

목적이 둘이고 순서가 있다.

1. **쓸 만한 서비스를 만든다.** 자료가 맞아야 하고 기능이 닫혀 있어야 한다.
2. **다만 기술 선택은 배울 것이 많은 쪽으로 기운다.** booster 저장소의 성격이 그렇다.

그래서 이 문서의 요구사항 표에는 **「비계」 칸**이 있다 — 이 기능이 무슨 기술을 세우는
자리인가. **그 칸이 비는 기능은 후순위로 밀 근거가 된다.** 기능 갯수를 늘리는 것 자체는
목적이 아니다.

## 3. dday-static 과의 관계 — 완전 분리

`frontends/dday-static` 은 **손대지 않는다. 자료도 코드도 가져오지 않는다.**
독립된 서비스로 그대로 두다가 이 리뉴얼이 끝나면 비활성화한다.

그쪽이 무엇을 제공하는지는 **범위의 눈금으로만** 쓴다 — "정적이 하던 것 전부"가
이 서비스의 바닥이기 때문이다. 자료는 전부 원천(Nager 등)에서 새로 세우고,
계산은 전부 이쪽에서 새로 구현한다.

### 대가 — 두 개의 진실

분리를 택했으므로 `this-is-the.day`(월 1회 빌드)와 이 서비스(자체 동기화)가 같은
원천을 각자 읽는 기간이 생긴다. **어느 한쪽이 늦으면 같은 나라 같은 날이 두 곳에서
다르게 보인다.** 이것은 설계 결함이 아니라 분리의 대가다. 버그로 오해하지 않도록
여기 적어 둔다. dday-static 을 끄는 시점에 이 항목은 사라진다.

## 4. 왜 서버인가 — 게이트 넷

정적 쪽에는 "자료를 하나 더 붙일지" 를 정하는 게이트 넷이 있다. 새 서비스가 담을
자료들을 그 넷에 걸어 보면, **왜 서버가 필요한지가 자료 자체에서 나온다.**

| 게이트 | 공휴일 | 개인 기념일 | 영화 · 스포츠 |
| --- | --- | --- | --- |
| 미래 날짜가 미리 확정되는가 | 예 (연 단위) | **아니오** — 사용자가 아무 때나 | **아니오** — 개봉 연기 · 일정 변경 |
| 축이 맞는가 | 예 | **아니오** — 사용자마다 다름 | 새 축이 필요 |
| 키 없이 받는가 | 예 (Nager 무키) | 해당 없음 | **아니오** — TMDB · TheSportsDB |
| 검산점이 있는가 | 예 | 해당 없음 | **재봐야 한다** |

**새 백엔드는 이 게이트를 통과하지 못한 자료들의 집이다.** 공휴일은 그 위에 깔리는
공통 바닥이고, 그 바닥이 있어야 개인 기념일과 영화가 "이 날은 공휴일이라 쉰다" 를
말할 수 있다.

## 5. 되찾아야 할 표면

정적 사이트의 실측 규모다. **우리가 다시 세워야 할 양이지, 가져올 양이 아니다.**

- HTML 548장 = 한국어 274 + 영어 274
- 한국어 274 = 국가 204 + 이름 낱장 60 + 이름 허브 1 + 순위 1 + 요일 1 + 하늘 6 + 홈 1
- 국가 자료 204벌 — 나라마다 `days[{날짜, 이름ko, 이름en}]` 과 `long[{시작, 끝, 징검다리}]`
- 하늘 한 벌 (3년치) — 절기 72 · 삭망 74 · 유성우 30 · 음력 37 · 달력 21
- 월별 역인덱스 36벌 (3년 × 12개월) — "오늘 공휴일인 나라"

정적 쪽이 재 둔 수치 둘. **우리 자료로 다시 재서 맞는지 봐야 한다** — 검산점이 된다.

- 주말이 토·일인 나라 195, **금·토 8개국, 일요일 하루뿐인 나라 1개국(인도)**
- 2026년 (국가, 날짜) 2,500쌍 중 주말에 겹쳐 날아간 공휴일 **544 (21.8%)**.
  토·일 고정으로 세면 540 이 나온다 — 그 **네 건의 차이**가 나라별 주말을 보고
  있는지 아닌지를 가른다.

## A. 공휴일 — 읽기 바닥

| | 요구사항 | 비계 | 상태 |
| --- | --- | --- | --- |
| A-1 | 국가 하나의 공휴일을 연도별로 본다 (204개국 · 최소 3년) | Cache-Aside · 204키 분포 | 확정 |
| A-2 | 국가 하나의 다음 공휴일 D-day | 〃 | 확정 |

| A-4 | 오늘 공휴일인 나라 목록 (날짜 → 국가 역방향) | 역인덱스 | 확정 |
| A-5 | 이름으로 묶어 본다 — "크리스마스에 쉬는 나라 178개국" | 집계 질의 · 인덱스 설계 | 확정 |

| A-8 | 한국어 · 영어 | 응답 로케일 | 확정 |
| A-9 | 지역 한정 공휴일(일부 주만 쉬는 날)을 **넣고 표시한다** | — | 확정 |
| A-10 | `Public` 만 노출하되 원래 `type` 은 저장해 둔다 | 필터 축 | 확정 |

**A-5~A-7 은 자료를 하나도 더 만들지 않는 파생이다.** 정적 쪽이 그렇게 했고, 그 성질을
지키는 편이 낫다 — 미리 계산해 저장하면 원본과 갈라질 수 있고 그러면 그것까지
검증해야 한다. 대신 **Redis 캐시가 그 자리**다 (정적에서 CDN 이 맡던 자리).

**A-10 의 이유:** 지금은 `Public` 만 내보내도, `Bank` · `Observance` 를 저장해 두면
나중에 축을 열 때 **재동기화가 필요 없다.** 버리는 것은 되돌릴 수 없다.

| | 요구사항 | 비계 | 상태 |

| B-4 | 음력 ↔ 양력 | 〃 | 확정 |
| B-5 | 다른 달력 (단기 등) | 축이 하나 늘 뿐 | **뒤로** |
| B-6 | **임의 연도 질의를 받는다** | 캐시 히트율 · 계산 비용 | 확정 |

**B 는 DB 없이 캐시만 쓰는 유일한 도메인이다.** 다른 도메인의 대조군이 된다.

**B-6 이 중요한 이유:** 정적이 3년에 묶였던 것은 빌드 타임이기 때문이다. 임의 연도를
받는 순간 **서버가 정적을 이기는 지점이 하나 생긴다.** 서버의 존재 증명이다.

**미결:** 천문 계산을 어떻게 세울지는 정하지 않았다. dday-static 에서 가져오지
않으므로 Java 로 처음부터 구현해야 하고, 이는 만만치 않다 (VSOP87 절단 · Meeus ·
ΔT · 유성우 황경). **검산점을 먼저 확보하고 착수한다** — 분점·지점 공표 시각처럼
바깥에서 확인 가능한 값. 값 없이 짓고 나서 "검산할 게 없네" 를 발견하면 늦는다.

## D. 영화 · 스포츠 — 외부 연동

| | 요구사항 | 비계 | 상태 |
| --- | --- | --- | --- |
| D-1 | 개봉 예정 영화 D-day | **CircuitBreaker · Bulkhead · RateLimiter** | 확정 |
| D-2 | 경기 일정 D-day | 〃 | 확정 |
| D-3 | 관심 등록 | C 와 같은 쓰기 도메인 | 확정 |
| D-4 | **개봉일이 밀렸을 때 알린다** | 변경 감지 → 이벤트 → 알림 | 확정 |
| D-5 | 스포츠는 **종목 불문 범용 모델**, 켜는 리그는 설정값 | 외부 자료 모양에 안 끌려다니기 | 확정 |

**D-1 · D-2 는 이 서비스에서 CircuitBreaker 를 정직하게 쓸 유일한 자리다.** 내부
호출에 걸어 두는 것과 달리 여기는 진짜 남의 서버이고 진짜로 죽는다.

**D-4 가 없으면 D 는 그냥 외부 API 프록시다.** 이 한 줄이 D 를 C 와 잇고, 변경 감지 →
이벤트 발행 → 알림이라는 사슬을 만든다.

### D-5 — 범용으로 가되, 켜는 범위는 설정으로 자른다

종목 하나를 고르는 대신 **모델과 API 를 종목 불문 범용**으로 짓는다 —
`sport / league / team / event` 의 일반 구조. 코드에 특정 리그를 박지 않는다.

**다만 「어디까지 담을까」는 사라지지 않고 자리를 옮긴다.** 셋 때문이다.

1. **범용은 관심 등록(D-3)을 선택이 아니라 전제로 만든다.** 전 세계 경기를 다 담으면
   하루에 수백 건이고, 그러면 "다음 경기 D-day" 가 의미를 잃는다. 내가 고른 팀이
   있어야 D-day 가 성립한다.
2. **동기화 범위는 여전히 잘라야 한다.** 외부 API 가 리그 단위로 주므로 전부 당기면
   수만 건에 매일 갱신이다.
3. **검산점(게이트 4)이 약해진다.** 좁으면 "이 리그 2026 정규시즌이 몇 경기인가" 로
   검산되는데, 범용이면 "받은 대로 찍혔나" 밖에 볼 것이 없다.

**그래서 실제로 동기화하는 리그 목록은 설정값이다.** 1차에는 한둘만 켜고 늘릴 때
코드를 고치지 않는다. 검산점은 켜 둔 리그마다 시즌 경기 수로 잡는다.
「지금 종목을 골라라」 가 「지금 어떤 리그를 켤까」 로 바뀌었고, 후자는 언제든
되돌릴 수 있는 운영 결정이다.

## E. 횡단

| | 요구사항 | 비계 | 상태 |
| --- | --- | --- | --- |
| E-1 | **시간대 정확한 D-day** — 국가별 대표 시간대 기준 | CLDR 국가→시간대 | 확정 |
| E-2 | **통합 검색** — 공휴일 이름 · 국가 · 영화 · 스포츠 · 내 기념일 전부 | 이질 소스 통합 · 색인 · 권한 필터 | 확정 |
| E-3 | 조회수 기반 실시간 인기 | **Redis SortedSet** | 확정 |
| E-4 | 운영자 — 수동 동기화 · 상태 조회 | **ShedLock** · 수동 트리거 | 확정 |

**E-1 은 서버의 존재 이유다.** 정적 쪽은 보는 사람의 기기 날짜로 D-day 를 계산해서
다른 시간대 국가를 볼 때 하루 어긋나고, 그것을 각주로만 적어 두었다 (CLDR 표를
들여와야 해서). **서버는 그 표를 들일 수 있다.** 정적이 못 고친 고장을 새 서비스가
정면으로 고치는 항목.

**E-3 의 구조는 waiting-service 가 대기 순번에 쓰는 그 SortedSet 이다.** 같은 도구를
다른 문제에 쓰는 셈이라 비교가 된다.

### E-2 — 통합 검색이 D 의 성격을 바꾼다

검색 대상이 전부다. 공휴일 이름 · 국가 · 영화 제목 · 팀과 경기 · 내 기념일.
**이 결정에는 도메인을 건드리는 파급이 둘 있다.**

**하나 — 영화와 스포츠를 우리가 갖고 있어야 한다.** 검색하려면 색인이 필요하고,
색인하려면 저장해야 한다. 그래서 D-1 · D-2 가 **「요청이 올 때 외부를 호출한다」에서
「주기적으로 당겨와 저장하고, 검색은 우리 것을 본다」로 바뀐다.** 외부 호출은
동기화 경로로 물러나고, 읽기 경로에서는 빠진다. CircuitBreaker 가 지켜야 할 것도
사용자 요청이 아니라 동기화 작업이 된다.

**둘 — 한 응답에 공개 자료와 남의 것이 아닌 자료가 섞인다.** 내 기념일이 대상에
들어오는 순간, 같은 질의가 사람마다 다른 결과를 낸다. **결과 필터가 사용자별이므로
검색 응답은 캐시 키에 사용자를 포함해야 하거나, 공개 축과 개인 축을 나눠 합쳐야 한다.**
이 서비스에서 캐시 전략이 갈라지는 유일한 지점이다.

| F-4 | 자료 동기화가 중복 실행되지 않는다 (분산 락) | 확정 |
| F-5 | **p99 를 통과 조건으로 둔다** (아래 표). 목표 RPS 는 두지 않고 측정한다 | 확정 |

**F-5 를 비워 두면 안 되는 이유:** "대용량" 이 수치 없이 남으면 캐시가 충분한지 판단할
기준이 없고, 부하 테스트가 **통과 조건 없는 의식**이 된다.

### F-5 — p99 를 통과 조건으로 둔다

`docs/performance-test-slo-rps-guide.md` 는 **목표 RPS(비즈니스 요구사항)** 와
**최대 처리 가능 RPS(측정 결과)** 를 섞지 말라고 적어 두었다. 이 서비스에는
**비즈니스 예상 사용량이 없다** — 그러니 목표 RPS 를 지어내지 않는다.
대신 **p99 를 통과 조건으로 걸고, 그 조건을 지키며 몇 RPS 까지 가는지를 측정값으로
기록한다.**

| 갈래 | 해당 | p99 |
| --- | --- | --- |
| 캐시 히트 읽기 | A-1~A-4 · B | **< 100 ms** |
| 파생 축 집계 | A-5~A-7 | **< 300 ms** |
| 통합 검색 | E-2 | **< 300 ms** |
| 개인 기념일 쓰기 | C-2 · C-4 | **< 300 ms** |
| 외부 연동이 읽기 경로에 남은 것 | D 잔여 | **< 1,000 ms** |

에러율은 갈래 불문 **< 1%**. CircuitBreaker 가 열린 상태에서도 위 p99 를 지켜야 한다
— 열린 회로가 느린 타임아웃으로 나타나면 차단의 뜻이 없다.

**저장소 관례에서 갈라지는 점을 적어 둔다.** query-burst-msa 는 p95 를 쓰고
부하 테스트 스크립트와 Grafana 패널이 그 위에 서 있다. 여기서 p99 를 택한 것은
의도적이며(더 엄격하다), **부하 테스트를 세울 때 임계값을 p95 에서 베껴 오면
조용히 느슨해진다.**

## 6. 표에서 드러난 것

**셋만이 도메인을 가로지른다.** 나머지는 전부 자기 도메인 안에서 닫힌다.

| | 무엇을 가로지르나 | 무엇을 흔드나 |
| --- | --- | --- |
| C-7 | 개인 기념일이 하늘(음력 계산)을 소비한다 | 도메인 경계 |
| D-4 | 외부 자료의 변경이 알림 사슬을 탄다 | 이벤트 흐름 |
| E-2 | 통합 검색이 **다섯 도메인을 전부** 읽는다 | 색인 · 캐시 키 · 권한 |

비계 관점에서 이 셋의 값어치가 제일 크고, 동시에 **설계를 제일 많이 흔들 항목**이다.
그러므로 **초반에 둔다.** 나중에 끼우면 이미 굳은 경계를 뚫어야 한다.

E-2 가 셋 중 가장 늦게 들어왔는데(2026-09-11) 파급은 가장 크다 — 혼자서 D 의 성격을
바꾸고(§E-2) 캐시 전략을 둘로 가른다. **검색을 나중에 얹기로 했다면 D 를 외부 호출
프록시로 지었을 것이고, 그러면 검색을 넣는 날 D 를 다시 지어야 했다.**

## 7. 닫힌 결정

열린 물음 셋은 **2026-09-11 에 닫혔다.**

| | 물음 | 답 |
| --- | --- | --- |
| E-2 | 검색의 대상 | **전부** — 공휴일 이름 · 국가 · 영화 · 스포츠 · 내 기념일 |

### 이 결정들이 남긴 것 — 설계 단계에서 정한다

요구사항은 닫혔지만, 답이 새 결정을 낳았다. **이것들은 요구사항이 아니라 설계다.**

1. **1차에 켤 리그.** D-5 가 "종목 고르기" 를 "리그 켜기" 로 바꿨으므로, 언제든
   되돌릴 수 있는 운영 결정이 되었다. 착수 시점에 하나 고르면 된다.
2. **검색 색인을 무엇으로 세우나.** DB 인덱스로 버틸지, 별도 색인이 필요한지.
   대상이 다섯 도메인이고 두 언어다.
3. **검색 응답의 캐시 키.** 개인 기념일이 섞이므로 사용자별로 갈라야 한다 (§E-2).
4. **천문 계산의 검산점.** 짓기 전에 확보한다 (§B).

# 9. 도메인 모델 (초안)

> 2026-09-11. 엔티티 필드는 설계 착수 시 스키마와 함께 확정한다.
> 여기서 정하는 것은 **경계와 소유권**이다 — 무엇이 어느 도메인의 것인가.

## 9.1 컨텍스트 지도

```
                        ┌───────────┐
                        │  country  │  국가 코드 · 이름 · 대표 시간대 · 주말
                        └─────┬─────┘  (거의 안 변하는 참조 자료)
            ┌─────────────────┼─────────────────┐
            ▼                 ▼                 ▼
      ┌──────────┐      ┌──────────┐      ┌──────────┐
      │ holiday  │      │ release  │      │   sky    │  DB 없음 · 계산 + 캐시
      │  코퍼스   │      │ 영화·경기 │      └────┬─────┘
      └────┬─────┘      └────┬─────┘           │
           ▼                 │                 │ C-7 음력
      ┌──────────┐           │                 ▼
      │   axis   │           │           ┌─────────────┐
      │ 읽기 전용 │           └──────────▶│ anniversary │
      └────┬─────┘  D-3 관심   (공유 알림) │  개인 기념일 │
           │                              └──────┬──────┘
           └──────────────┬──────────────────────┘
                          ▼
                    ┌──────────┐
                    │  search  │  E-2 — 다섯을 전부 읽는다
                    └──────────┘
```

**화살표의 뜻은 「읽는다」이다.** 어느 도메인도 남의 것을 쓰지 않는다.
가로지르는 셋(§6)이 이 그림에서 화살표 셋으로 보인다 — `sky → anniversary`(C-7) ·
`release → 알림`(D-4) · `모두 → search`(E-2).

## 9.2 `country` — 참조 자료

| 집합체 | 담는 것 |
| --- | --- |
| `Country` | 코드(ISO 3166-1 alpha-2) · 영어 이름 · 한국어 이름 · **대표 시간대** · **주말 요일** |

**동기화 대상이 아니다.** CLDR 에서 한 번 뽑아 시드로 넣고 판을 박는다. 국가 목록과
시간대는 자주 바뀌지 않고, 바뀌면 그것 자체가 사람이 확인할 사건이다.

- **대표 시간대**가 E-1(시간대 정확한 D-day)의 근거다. 한 나라에 시간대가 여럿인
  경우(미국 · 러시아)는 **대표 하나를 고르고 그 사실을 응답에 표시한다.** 조용히
  고르면 사이트가 거짓말을 한다.
- **주말 요일**이 A-7(요일 축)의 근거다. 토·일이 아닌 나라가 있다.
- **국기는 담지 않는다.** JSON API 전용이므로(§1) 이미지 자산은 프론트 몫이고,
  우리는 국가 코드만 준다.

## 9.3 `holiday` — 공휴일 코퍼스

| 집합체 | 담는 것 |
| --- | --- |
| `Holiday` | 국가 · 날짜 · 현지어 이름 · 영어 이름 · 전국 여부 · 지역 코드 · **타입 전부** · 최초 시행 연도 |
| `HolidayNameLabel` | 영어 이름 → 한국어 라벨 (§9.9 참고) |
| `LongWeekend` | 국가 · 시작 · 끝 · 징검다리 날짜 |
| `SyncRun` | 동기화 이력 — 대상 · 시각 · 결과 건수 · **버린 건수** |

- **같은 날 두 건이 정상이고, 같은 날 같은 이름 두 건도 정상이다.** 앞은 대한민국
  2025-05-05(어린이날 + 부처님 오신 날), 뒤는 스위스처럼 **칸톤마다 쪼개져 오는**
  경우다. 유일 제약은 **`(국가, 날짜, 영어 이름, 지역 집합)`** 넷이어야 한다 — 실측
  근거는 §11.3.
- **`Public` 이 아닌 타입도 저장한다** (A-10). 노출만 막는다. 버리면 축을 열 때
  전체 재동기화가 필요하다. **`types` 는 배열이고 실제로 복수 값이 온다**
  (`Public+Bank` · `Bank+Optional`). 그러므로 필터는 같음 비교가 아니라
  **"`Public` 을 포함하는가"** 다 (§11.2).
- **징검다리 날짜를 원천이 준다.** 계산하지 않는다 (`bridgeDays`). `dayCount` 도
  주지만 **담지 않는다** — 시작과 끝에서 나오는 값을 따로 담으면 둘이 갈라질 수 있고,
  그러면 그것까지 검증해야 한다.
- **`LongWeekend` 가 우리 코퍼스에 걸려 있는지 확인한다.** 원천이 타입을 가리지 않고
  연휴를 줄 수 있으므로, 우리가 담지 않은 공휴일에만 걸린 연휴는 버린다 — 안 그러면
  표에 없는 날을 근거로 "5일 연휴" 라고 적는 응답이 나온다. **버린 건수를 `SyncRun` 에
  남긴다.** 다만 실측(45개국 · 2026)에서는 **0건**이었다 (§11.4) — 규칙은 방어로
  두되, 이것이 자주 발동하리라 기대하고 설계하지 않는다.

## 9.4 `axis` — 읽기 전용 파생

**집합체가 없다. 테이블도 없다.** 질의 + 캐시로만 산다 (§A 의 원칙).

| 읽기 모델 | 답하는 물음 |
| --- | --- |
| `NameAxis` | 이 이름으로 쉬는 나라는 어디인가 (A-5) |
| `RankAxis` | 공휴일 수 · 최장 연휴로 견주면 (A-6) |
| `WeekdayAxis` | 주말에 겹쳐 날아간 공휴일은 (A-7) |
| `DayIndex` | 오늘 쉬는 나라는 (A-4) |

파생물을 저장하지 않는 대신 **집계 질의가 무거워진다.** 그 무게를 캐시가 받는다 —
이것이 §F-1(캐시가 1급 설계 대상)의 실제 내용이고, `axis` 가 이 서비스의 캐시 설계를
가장 세게 미는 자리다.

## 9.5 `sky` — 계산

**DB 를 쓰지 않는다.** 순수 계산 + 결과 캐시. 다른 도메인의 대조군이다 (§B).

| | |
| --- | --- |
| 도메인 서비스 | 절기 · 삭망 · 유성우 · 음력 변환 |
| 값 | 계산 결과 (저장하지 않음) |
| 캐시 키 | (갈래, 연도) — B-6 이 임의 연도를 받으므로 키 공간이 열려 있다 |

**임의 연도(B-6)가 캐시에 주는 부담을 설계 때 재야 한다.** 사람이 실제로 묻는 연도는
좁을 것이나(올해 앞뒤), 키 공간 자체는 무한이다. 캐시 오염 방어가 필요하다.

## 9.6 `anniversary` — 개인 기념일

| 집합체 | 담는 것 |
| --- | --- |
| `Anniversary` | 회원 · 제목 · 기준일 · **달력 갈래(양력/음력)** · 윤달 여부 · 반복(없음/매년) · **세는 방향(D-day / D+N)** · 기준 시간대 · 알림 시점 |
| `MemberReference` | auth-service 에서 Kafka 로 받아 둔 회원 참조 |

- **음력(C-7)이 `sky` 를 소비하는 유일한 지점이다.** 음력 기념일의 다음 발생일을
  구하려면 음력→양력 변환이 필요하다.
- **세는 방향이 둘이다** (C-8). 생일은 다음 발생일까지 세고(D-day), "만난 지" 는
  기준일부터 센다(D+N). 한 필드로 가른다.
- **회원을 이 서비스가 소유하지 않는다.** auth-service 가 원본이고 여기는 참조뿐이다.

## 9.7 `release` — 영화 · 스포츠

종목 불문 범용 (§D-5). **다만 영화와 경기를 한 집합체로 억지로 합치지 않는다.**

| 집합체 | 담는 것 |
| --- | --- |
| `Movie` | 작품 · **국가별 개봉일** |
| `League` / `Team` / `SportEvent` | 종목 · 리그 · 팀 · 경기 (리그 목록은 설정값) |
| `Watch` | 회원의 관심 등록 (D-3) |
| `DateChange` | 날짜가 바뀐 이력 — D-4 알림의 근거 |
| `SyncRun` | 동기화 이력 |

**공통은 인터페이스로만 둔다** — "날짜를 가진 것" 으로서 D-day 계산과 검색 색인에
같은 모양으로 참여한다. 저장 구조까지 합치면 두 자료의 다른 점이 뭉개진다.

- **영화는 국가별로 개봉일이 다르다.** `country` 축과 곱해진다 — 공휴일과 같은 모양의
  문제다. "개봉 D-day" 는 **어느 나라 기준인지 없이는 성립하지 않는다.**
- **`DateChange` 가 없으면 D-4 가 성립하지 않는다.** 동기화할 때 이전 값과 견주어
  달라진 것만 기록하고, 그 기록이 이벤트가 된다.

## 9.8 `search` — 통합 검색

| | |
| --- | --- |
| `SearchDocument` | 갈래 · 참조 id · 한국어 제목 · 영어 제목 · **소유자(개인 자료만)** |

- **소유자 칸이 있는 것과 없는 것이 한 색인에 섞인다** (§E-2). 공개 자료는 소유자가
  비어 있고, 개인 기념일만 채워진다. 질의할 때 `소유자 IS NULL OR 소유자 = 나` 로
  거른다.
- **색인을 별도로 세울지, 각 도메인 테이블을 직접 질의할지는 아직 결정이 아니다**
  (§7 남은 결정 2번). 위 표는 "별도 색인" 쪽 초안이다.

## 9.9 모델을 세우다 걸린 것 넷

### (1) 공휴일 이름의 한국어가 원천에 없다 — **확인됨 (§11)**

A-8 은 "한국어 · 영어" 를 요구하는데, Nager 가 주는 것은 **현지어 이름과 영어 이름
둘뿐이다.** 한국 공휴일은 현지어가 곧 한국어라 문제가 안 보이지만, **일본 공휴일의
현지어는 일본어다.**

| 무엇의 한국어 | 원천 |
| --- | --- |
| 국가 이름 | CLDR — 있다 |
| 공휴일 이름 | **없다** |

그래서 `HolidayNameLabel` 이 필요하다 — 영어 이름을 키로 한국어 라벨을 손으로 적는
표. 전부 적을 수는 없으므로(수천 가지) **문턱을 넘는 이름만 적고, 라벨이 없으면
영어 이름으로 떨어뜨린다.**

> **2026-09-11 에 원천을 직접 받아 확인했다 (§11).** 일본 2026 의 `localName` 이
> `元日` · `成人の日` 다. 응답 아홉 필드 어디에도 한국어가 없다.
> `HolidayNameLabel` 은 필요하다.

### (2) D-day 를 응답에 담으면 캐시가 자정에 묶인다

D-day 는 **날마다 바뀌는 값**이다. 캐시하는 응답에 그대로 박으면 TTL 이 자정까지로
묶이고, 시간대가 204가지이므로 **자정이 하루에 여러 번 온다.**

갈래가 둘이다. 설계에서 하나를 고른다.

| | 방법 | 대가 |
| --- | --- | --- |
| 가 | 캐시에는 날짜만 담고, D-day 는 응답을 내보낼 때 덧붙인다 | 캐시가 날짜에 독립 — 대신 조립 단계가 생긴다 |
| 나 | 캐시 키에 "그 시간대의 오늘" 을 포함한다 | 단순 — 대신 키가 시간대 수만큼 갈라진다 |

**정적 쪽은 이 문제를 만나지 않았다.** 브라우저가 계산했기 때문이다. 서버가 D-day 를
계산하기로 한 순간(E-1) 생기는 값이다.

### (3) 게이트웨이 라우팅이 새 표면을 못 덮는다

지금 라우팅은 `Path=/api/v1/special-days/**` 하나이고, `JwtAuthorizationFilter` 도
그 경로에 `"d-day"` 권한을 매단다. **새 API 는 공휴일 · 하늘 · 기념일 · 영화 · 검색으로
퍼지므로 이 한 줄로는 안 태워진다.** §10.1 에서 정한다.

### (4) 한 나라에 시간대가 여럿일 때

미국 · 러시아 · 호주. 대표 하나를 고를 수밖에 없는데, **고른 사실을 응답에 표시한다.**
E-1 이 고치려던 것이 "조용히 하루 어긋남" 이었으므로, 그 자리에 "조용히 대표 시간대로
퉁침" 을 새로 만들면 고친 것이 아니다.

# 11. 원천 확인 — Nager.Date v3

> 2026-09-11. **기억이 아니라 실제 응답을 받아 적은 것이다.**
> 표본: `AvailableCountries` 전수(204) + 앞 45개국의 2026년 공휴일 612건 · 황금연휴 330건.

## 11.2 `types` 는 배열이고 실제로 복수가 온다

45개국 · 2026 · 612건의 분포.

| 조합 | 건수 |
| --- | --- |
| `Public` | 589 |
| `Observance` | 12 |
| `School` | 5 |
| `Bank` | 3 |
| **`Bank` + `Optional`** | 2 |
| `Optional` | 1 |

미국에서는 **`Public` + `Bank`** 가 10건 나왔다.

**그러므로 A-10 의 필터는 같음 비교가 아니라 포함 비교다.** `types == 'Public'` 으로
짜면 `Public+Bank` 인 미국 공휴일 10건이 통째로 사라진다. 조용히 사라지므로
눈에 띄지도 않는다.

## 11.3 자연키가 성립하지 않는다 — 스키마에 직접 영향

45개국 · 2026 에서 키 후보 둘을 실제로 세어 보았다.

| 키 후보 | 충돌 |
| --- | --- |
| `(국가, 날짜, 영어 이름)` | **11조** |
| `(국가, 날짜, 영어 이름, 지역 집합)` | **0조** |

충돌한 11조 중 10조가 **스위스**다 — `Epiphany` · `Saint Joseph's Day` ·
`Easter Monday` · `Labour Day` … 이 전부 같은 날 같은 이름으로 **두 건**씩 온다.
칸톤 집합이 다르기 때문이다. 나머지 하나는 **호주 `Anzac Day`** 다.

> 스위스 2026-01-06 `Epiphany` 가 두 건. 미국 2026-04-03 `Good Friday` 도
> counties 10개짜리 하나와 `US-TX` 하나로 두 건이다.

**결론 — 유일 제약은 넷이다.** `(국가, 날짜, 영어 이름, 지역 집합)`.
`(국가, 날짜)` 로 걸면 대한민국 2025-05-05(어린이날 + 부처님 오신 날)을 잃고,
`(국가, 날짜, 이름)` 까지 가도 스위스와 호주를 잃는다.

**"지역 집합" 을 어떻게 저장하고 어떻게 비교할지는 스키마 결정이다** — 정렬한
문자열로 굳힐지, 별도 테이블로 풀지. `db-tuner` 에 넘길 때 이 문단을 같이 넘긴다.

## 11.4 황금연휴는 (표본 안에서는) 전부 Public 에 걸려 있었다

45개국 · 2026 · 황금연휴 330건 전부가 **우리가 담을 `Public` 공휴일에 걸려 있었다.
버릴 것이 0건이었다.**

§9.3 의 버리기 규칙은 **방어로 남긴다** — 표본이 45개국 한 해일 뿐이고, 원천이
언제 타입을 섞어 줄지는 우리가 정하지 않는다. 다만 **이 규칙이 자주 발동하리라
기대하고 설계하지는 않는다.** `SyncRun` 의 "버린 건수" 는 평소 0 이어야 정상이고,
0 이 아니면 그것이 신호다.

# GPS 적재 배치 장애 분석 및 복구

> 운영 중인 차량 단말 데이터 수집 시스템에서, 9개월간 누락되던 GPS 데이터 5억 행을 복구하고
> 원인이 된 배치 구조 결함 4건을 수정한 작업 기록.

**기간** 2026-10-01 ~ 10-02 (2일)
**환경** Java 17 / Spring Boot 3.3 / Spring Batch / MyBatis / PostgreSQL 14 / AWS S3 / EC2
**규모** GPS 이력 테이블 단일 8억 행, 446GB (heap 339GB + 인덱스 107GB)

---

## 1. 문제 현상

세 가지가 겹쳐 있었고, 겉으로 드러난 것은 하나뿐이었다.

### 표면 — 쿼리 하나가 46시간 실행 중

`pg_stat_activity` 에서 GPS 링크 UPDATE 한 건이 **46시간째 실행 중**인 것을 발견.
대기 이벤트는 `LWLock / BufferMapping` 으로, 락 대기가 아니라 I/O 포화 상태였다.

### 숨어 있던 문제 1 — 매분 배치가 46시간 정지

`@Scheduled` 는 이전 실행이 끝나야 다음 발화 시각을 계산한다.
위 쿼리가 스레드를 점유한 46시간 동안 **매분 돌아야 할 마이그레이션 배치가 한 번도 발화하지
못했다.** 프로세스는 살아 있어 모니터링에 잡히지 않았다.

### 숨어 있던 문제 2 — 9개월간 데이터가 적재되지 않고 있었음

다른 DB를 점검하다 `migrate_flag='N'`(미처리) 레코드가 **2025-12-25부터 1,813건** 쌓여 있는
것을 발견. 통계를 확인하니 문제의 규모가 드러났다.

```
n_tup_ins   18,860,130,727   (80일간 INSERT)
n_live_tup     293,323,316   (실제 남은 행)
n_tup_upd        5,253,803
```

**INSERT 한 것의 98%가 사라지고 있었다.** 하루 2억 3,600만 건이 들어가는데 실제 증가는
370만 건으로, 단말 30여 대의 실제 발생량과 일치했다. 같은 데이터를 수십 번 다시 넣고
있었다는 뜻이다.

배치는 멈춘 적이 없었다. **일을 하고 버리고 있었기 때문에** 프로세스 감시로는 잡히지 않았고,
미처리 건수를 세는 알람도 없어 9개월간 아무도 몰랐다.

## 2. 원인 분석

### 원인 ① 레코드 단위 커밋이 실제로는 동작하지 않음

적재 코드는 레코드마다 `session.commit()` 을 호출하고 있었다. **그런데 그게 no-op 였다.**

mybatis-spring 의 `SpringManagedTransaction` 은 Spring 트랜잭션에 바인딩된 커넥션을 그대로
물어 쓰고, `commit()` 호출을 건너뛴다. 배치 스텝이 일반 `transactionManager` 를 쓰고 있었으므로
**실행 전체가 트랜잭션 하나**였고, 레코드 단위 커밋은 이름뿐이었다.

### 원인 ② 손상된 파일 1건이 큐 선두에 영구히 남아 있었음

단말이 올린 SQLite 파일 중 하나가 손상(`SQLITE_CORRUPT`)돼 있었다.
레코드별 예외 격리가 없어 예외가 배치 스텝까지 전파됐고, **그 실행에서 적재한 수백만 건이
통째로 롤백**됐다. 플래그도 `N` 으로 남아 다음 주기에 같은 일이 반복됐다.

약 40분마다, 9개월간.

### 원인 ③ 임시 파일 정리 누락에 의한 연쇄 실패

임시 경로가 레코드별이 아니라 **차량번호별**이어서 같은 차량의 모든 레코드가 같은 파일을
공유했다. SQLite 가 WAL 모드로 동작해 `.db-wal` 을 만드는데, S3 다운로드는 `.db` 만
덮어쓰고 `-wal` 은 건드리지 않았다.

→ 한 레코드가 실패해 정리되지 못한 WAL 이 남으면, 다음 레코드가 받은 새 `.db` 와 짝이 맞지
않아 멀쩡한 파일까지 손상으로 읽혔다. **차량 한 대에서 한 번 실패하면 그 차량의 남은 레코드가
전부 끌려갔다.**

실패 분포가 이를 뒷받침했다 — 특정 단말에 367건, 268건씩 몰려 있었다.

### 원인 ④ 링크 쿼리의 대상 구간이 무제한

GPS 를 운행 구간에 연결하는 UPDATE 의 시작 시각(`period`)이 "미링크 행 중 가장 이른 시각"
이었다. 어떤 운행에도 속할 수 없는 행이 하나라도 있으면 **그 시각에 영구히 고정**되어,
매분 몇 달치 구간을 처음부터 다시 스캔했다. 46시간 쿼리의 직접 원인이다.

### 원인 분석 과정에서의 오판 정정

초기에는 `device_history_id IS NULL` 가드 누락(이미 링크된 행을 반복 UPDATE)을 주원인으로
판단했으나, **`n_tup_upd` 가 525만에 불과한 것으로 반증**됐다.
죽은 튜플이 많다고 UPDATE 를 의심하면 틀린다는 것, `n_tup_ins / n_tup_upd / n_tup_del` 로
먼저 연산 종류를 가려야 한다는 것을 이 과정에서 확인했다.

## 3. 해결

### 코드 (4개 모듈 공통 적용)

| 수정 | 내용 |
|---|---|
| 트랜잭션 경계 분리 | 배치 스텝을 `ResourcelessTransactionManager` 로 전환. 레코드마다 `autoCommit` 제어 후 커넥션에 직접 커밋해 실제 레코드 단위 커밋을 보장 |
| 실패 레코드 격리 | 레코드별 `try/catch` + `migrate_flag='E'` 로 큐에서 제외. 손상 파일 1건이 전체를 막지 못하게 함 |
| 임시 파일 선정리 | S3 다운로드 직전에 대상 경로의 `.db` / `-wal` / `-shm` 제거. 연쇄 실패 차단 |
| 링크 구간 제한 | `clampLinkPeriod` 로 대상 구간 하한을 최근 N일로 고정 + MyBatis `timeout` 으로 실행 상한 |
| 링크 쿼리 최적화 | 조인 상대 테이블도 같은 기준으로 필터링해 불필요한 스캔 제거 |
| 링크 단말별 격리 | `@Transactional` 제거 + 단말별 `try/catch`. timeout 이 트랜잭션을 중단시켜 뒤 단말이 연쇄 실패하던 문제 해결 |
| 복구 API | 실패 레코드 조회 / 재시도 엔드포인트 추가 (`'E' → 'N'`, `'Y'` 는 중복 적재 방지를 위해 차단) |

### DB 운영

- `VACUUM (INDEX_CLEANUP OFF)` 로 죽은 튜플 **18억 5,270만 개를 1시간 33분에 제거**
  (PostgreSQL 14 는 dead TID 배열이 1GB 로 제한되어, 일반 VACUUM 은 인덱스를 수십 회
  재스캔한다. 인덱스 정리를 분리해 heap 단일 패스로 처리)
- 중복 인덱스 식별 후 제거 — 복합 인덱스의 선두 컬럼과 겹치는 단일 컬럼 인덱스 (32GB 회수)
- `REINDEX CONCURRENTLY` 로 PK 인덱스 재생성 (80GB → 25GB, 2시간 35분, 무중단)
- 테이블 단위 autovacuum 임계치 조정 (`scale_factor` 0.2 → 0.02)

### 운영 개선

- 로그 보관 설정 수정 — `maxHistory` 누락으로 `totalSizeCap` 까지 무효화되어 압축 로그가
  영구 누적, 디스크 포화를 유발하고 있었음
- 레코드별 로그를 `debug` 로 분리. 조사 시점에 과거 기록이 남아있도록 평시 발생량 축소

## 4. 성과

| 항목 | 전 | 후 |
|---|---|---|
| 미처리 적재 건수 | 1,813건 (9개월 누적) | **0건** |
| 살아있는 GPS 행 | 2억 9,332만 | **8억 489만** (+5억 1,156만) |
| 적재 실패 | 1,225건 | **17건** |
| 죽은 튜플 | 18억 5,539만 | 0 (정리 완료) |
| 인덱스 크기 | 186GB | **99GB** |

- **9개월간 유실되던 GPS 5억 1,156만 행을 전량 복구 적재**
- 디스크 약 87GB 회수. 적재된 5억 행은 VACUUM 으로 확보한 내부 여유 공간을 재사용해
  **테이블 파일 크기 증가 없이** 수용됨 (44,387,575 블록 유지)
- 단일 쿼리가 배치 전체를 정지시키는 구조를 제거 — 최대 피해가 46시간에서 10분으로 제한됨

### 잔여 17건 — 단말 하드웨어 문제로 판별

복구되지 않은 17건은 전량 동일 단말의 파일이었다. SQLite 파일을 직접 분석해 원인을 특정했다.

- 파일 크기가 헤더의 페이지 수와 정확히 일치 → **전송 중 절단 아님**
- `change counter == version_valid_for` → **WAL 체크포인트 정상**
- 22,269 페이지 중 **1 페이지만** 손상, 그 안에서도 112 셀 중 12 셀만 손상
- 손상된 셀도 rowid 는 순차적으로 멀쩡하고 **페이로드 길이 필드만** 깨짐

→ 전송·프로토콜 문제가 아닌 **저장장치 쓰기 오류**로 판별. 249만 행 중 13행만 손실이며
나머지는 복구 가능함을 확인. 해당 단말이 운용 중단 상태여서 복구는 보류하고
단말팀에 저장장치 점검을 요청했다.

## 5. 구조적 원인과 재발 방지

### 같은 코드가 4벌 복제되어 있었다

배치 코드가 4개 모듈에 소스 복제로 존재했고, 수정이 자동 전파되지 않았다.

- 2026-06 에 한 모듈에서 동일 결함을 수정했으나 **원본 모듈에는 반영되지 않았다**
- 그 모듈은 2026-01 이후 8개월간 커밋이 없었고, 미처리 적재가 시작된 2025-12 는
  그 공백 직전이었다
- **격리 로직 보유 여부가 죽은 튜플 수와 정확히 대응** — 0 / 1,620만 / 18억 5천만

이번 수정은 4개 모듈에 동시 적용했고, 중단된 모듈에서도 **호출 즉시 실패하는 코드**를
발견해 함께 수정했다.

### 탐지가 안 된 이유

- 배치가 멈춘 게 아니라 **일을 하고 버리고 있어** 프로세스 감시로 잡히지 않음
- 미처리 건수를 보는 알람 없음
- 에러 로그는 40분마다 찍히고 있었으나 보는 주체 없음
- 증상(인덱스 비대)만 보고 **원인을 묻지 않은 채** 인덱스를 재생성한 적이 있었고,
  8일 만에 원래 크기로 돌아왔음

**가장 싼 재발 방지는 알람 한 줄**이라는 결론. 미처리 레코드의 최고령이 임계를 넘으면
알리는 것만으로 9개월이 아니라 하루 만에 발견할 수 있었다.
